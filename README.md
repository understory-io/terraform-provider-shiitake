# terraform-provider-shiitake

Terraform provider for the **shiitake slice registry** — the set of data-mesh slices shiitake-server provisions and schedules.

## Why this exists

Slice registration used to be a command someone ran:

```sh
shiitake schedule register --name google-ads-batch --project canopy-models \
  --domain marketing --image ghcr.io/understory-io/canopy-models/marketing/google-ads/batch:main
```

So a slice was registered because somebody remembered. `external/exchange-rates` is what that costs: it shipped its container images, its published fungus contracts and its ClickHouse grants, and **never ran once** — `dataset://external/fx-rates` was a live, subscribable contract with no table behind it, and nothing anywhere said so (DATA-590).

Nothing in CI closes that gap either. `canopy-models`' `build-slices.yml` builds and pushes an image per changed slice directory and stops there. `ScheduleService.SyncWorkspace` exists for exactly this, and its own proto comment calls itself *"the CI sync entry point"* — it had never been wired to anything.

Registration is desired **state**, not an event. This provider makes it a reviewable file, and makes deleting an entry prune the slice.

## Usage

```hcl
terraform {
  required_providers {
    shiitake = { source = "understory-io/shiitake" }
  }
}

# Reads SHIITAKE_SERVER and SHIITAKE_SERVICE_ACCOUNT_API_KEY from the environment.
provider "shiitake" {}

resource "shiitake_slice" "google_ads_batch" {
  name    = "google-ads-batch"
  project = "canopy-models"
  domain  = "marketing"
  image   = "ghcr.io/understory-io/canopy-models/marketing/google-ads/batch:e5d9e63"

  schedule = "0 */6 * * *" # omit or "" for a one-shot slice
  cpu      = "1024"
  mem      = "2048"
}
```

See `examples/resources/shiitake_slice/resource.tf` for the whole `canopy-models` workspace as one `for_each`.

## Two things that will bite you

### Pin the immutable tag, never `:main`

`RegisterSlice` upserts on the **spec**. A spec that says `:main` is unchanged even when the tag now points at a new build — so the server provisions nothing, launches nothing, and Terraform reports `No changes` forever while the slice runs last month's image.

This is not hypothetical: re-registering `google-ads-batch` on `:main` during DATA-590 produced no new task-definition revision and no run. Pinning the short sha bumped the revision and launched immediately.

`build-slices.yml` pushes `:main`, `:<timestamp>` and `:<short-sha>`. Use the sha.

### An apply runs the slice

Registering a one-shot slice does not merely record it — shiitake-server provisions the ECS task definition **and launches a run**. That is the intended behaviour (moving `image` and applying is how a slice picks up a new build), but it means `terraform apply` on this resource executes warehouse work. A no-change plan launches nothing.

## Resources

| | |
| - | - |
| `shiitake_slice` | Create/Update → `RegisterSlice`, Read → `GetSlice`, Delete → `PruneSlice`. Supports `terraform import <name>` so the hand-registered slices can be adopted without re-running them. |
| `shiitake_slices` (data source) | Every non-pruned entry. Useful for reconciling config against what is actually registered. |

## Development

The protos are **vendored** from `understory-io/shiitake` under `proto/`, not pulled from the BSR: `buf.build/understory-io/shiitake` is declared in that repo's `buf.yaml` but is not published, so a BSR-based `buf generate` fails on a clean machine. Generated Go lives in `gen/` and is committed, so `go build` works without buf installed.

```sh
scripts/vendor-proto.sh ../shiitake   # refresh protos + regenerate
go build ./...
```

A changed RPC in that diff is a provider change, not a formality.

### Testing against a real server

```sh
cat > /tmp/dev.tfrc <<'EOF'
provider_installation {
  dev_overrides { "understory-io/shiitake" = "/tmp/tfshiitake" }
  direct {}
}
EOF

go build -o /tmp/tfshiitake/terraform-provider-shiitake .
export TF_CLI_CONFIG_FILE=/tmp/dev.tfrc
export SHIITAKE_SERVER=https://shiitake-server.<your-env>:4000
export SHIITAKE_SERVICE_ACCOUNT_API_KEY=...   # from your secret store
terraform plan
```

The service-account key is generated by Terraform into your secret store, so read it from there rather than pasting it into a provider block.

**If you import a live slice into throwaway state, `terraform state rm` it when you are done.** A `destroy` against that state would prune a real slice.
